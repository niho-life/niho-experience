# `@niho-experience/experience-store`

PostgreSQL is the source of truth for provider-scoped experience products, recurring schedules, Google busy windows, booking holds, confirmed bookings, the payment ledger foundation, and guide drafts/publication snapshots.

## Trust boundary

- Host methods take `HostActor` and verify an active `provider_memberships` row. The caller must first authenticate the NIHO user; this package owns the experience-side membership check.
- Guest booking and worker methods take `ProviderScope`. The server route or worker must establish that provider scope before calling the store. Every SQL statement also filters by `provider_id`.
- Calendar storage accepts only an opaque calendar ID and interval boundaries. Event titles, descriptions, attendees, and OAuth credentials have no columns or API fields here.
- Stripe signatures and API calls stay outside this package. `confirmBookingPayment` accepts only a previously verified event and provides event deduplication, an append-only ledger entry, and an outbox message in the same transaction.
- Guide methods take a NIHO stable user ID after authentication. `guide_writer_grants` contains only globally accepted writer IDs. NIHO remains the source of truth for accounts, verified email, and the global writer grant. Provider-specific article-link invitations and consent are stored here using stable user IDs only; email, names, and private profiles are not copied.
- Provider `OWNER`/`EDITOR` authority and `guide_product_link_memberships` are separate. The latter permits only creation of an article/product relation and never grants product editing, booking, guest, or payout access. A guide remains creator-private even when its publication subject is a provider.
- A provider-subject guide can link only that provider's published products. A writer-subject guide can link products from any provider for which the link actor has current authority.
- Provider article-link invitations are separate from `provider_memberships`. Only a current provider `OWNER` can invite or revoke, only the target with a current writer grant can accept, and acceptance activates the existing `guide_product_link_memberships` projection. Re-invitation after decline/revoke advances a generation so stale acceptance requests cannot reactivate access.
- The future HTTP caller must obtain the stable writer ID through the separately deployed NIHO identity/display contract (#19462). This package is not a substitute for that resolution flow, and no browser user-ID input shortcut should be added.
- `getArticle` is the authenticated creator-only draft/preview read. Public reads select only a sealed `current_publication_id`; they never select draft columns. `UNLISTED` is still public to anyone who knows its slug and must be emitted as `noindex` by the later SSR layer. It is excluded from `listPublicArticles`. Stopping publication clears only the current pointer and preserves prior immutable snapshots.
- Guide cover assets are creator/article-scoped opaque UUIDs. Publication locks and rechecks the current `READY` asset and Web permission, then snapshots only alt/credit/asset ID. Public reads dynamically omit that snapshot after the asset becomes `REVOKED`.
- Guide `content` is a selected JSON object containing Markdown and public author metadata, never rendered HTML. This package does not render it. The editor/API must run the full Markdown, fact, image-rights, and related-record inspection before calling `commitPublication`; that server inspection and all HTTP exposure are intentionally outside this migration.

## Migrations

Apply `migrations/*.sql` in lexical order with the deployment migration identity. `0001_experience_store.sql` is transactional and does not require a PostgreSQL extension. Provider and first OWNER membership provisioning is intentionally outside the host repository API; onboarding must insert those rows from a separately authorized server workflow.

Both `0010_guide_body_media.sql` and `0010_shared_inventory.sql` exist. Apply both filenames in lexical order before `0011_guide_draft_product_links.sql`; the numeric prefix alone is not a unique migration identifier.

`0005_guide_cms.sql` additively creates guide categories, accepted writer/link grants, creator-private article drafts, sealed publication snapshots, and publication-scoped product links. Category and article slugs are stable identities; an article slug becomes immutable after its first publication. Category labels and order are copied into every publication so later category edits or deactivation do not rewrite history. `GuideRepository.commitPublication` locks the draft, verifies its revision/current authority/category/products, inserts the snapshot and authorized links, seals it, and switches `current_publication_id` in one transaction. Public link reads also require the product to remain `PUBLISHED` and the recorded link creator's permission basis to remain active.

`0008_guide_link_invitations.sql` additively creates the provider/writer consent state machine after calendar `0006` and channel `0007`. Invitation transitions serialize on the provider/writer pair, then lock invitation, owner, writer-grant, and projection rows in that order. Public link reads and `listLinkableProducts` require both an active accepted link projection and a current writer grant, so either provider revocation or writer-grant loss hides links without removing the public article body.

`0009_guide_media.sql` adds private cover assets, draft cover fields, and immutable publication-media snapshots. Asset identity/object location cannot change; rights can only advance from `UPLOADING` to `READY`/`REVOKED`, or from `READY` to `REVOKED`. Storage bytes remain outside PostgreSQL and object keys never enter browser DTOs.

`0020_provider_notification_preferences.sql` additively stores 設定 › 通知 (#109): one row per provider and stoppable notification (`GUEST_MESSAGE`, `DAY_BEFORE_SUMMARY`, `NEW_REVIEW`). A missing row means on, so existing providers need no backfill. `ProviderNotificationSettings.get`/`update` require a current OWNER membership that the server-established NIHO role ceiling does not cap; product operators never qualify. Senders call `enabledFor(providerId, key)` before a push or an email; the four locked notifications always answer true. No addresses, names or message text are stored. The runtime role needs SELECT/INSERT/UPDATE on the table.

`host-notification-outbox.ts` (#177 P2) uses the existing `outbox_messages` without a migration for the host app's push: `host.notify.approval_deadline` (6 hours and 1 hour before an approval deadline) and `host.notify.guest_message` (one per guest message). The booking and message transactions call `enqueueApprovalDeadlineReminders` / `cancelApprovalDeadlineReminders` / `enqueueGuestMessageNotification` in their own transaction once bookings move here (nothing calls them yet). Payloads are closed shapes (booking id, experience title, start, seats; no guest name, message text or amount). `HostNotificationOutbox.claimDue` claims only these topics with `FOR UPDATE SKIP LOCKED` and uses `available_at` as the lease; `complete` / `retryAt` touch only these topics, so `booking.confirmed` and other rows are never changed. The runtime role needs SELECT/INSERT/UPDATE on `outbox_messages`.

#285 slice 5 adds two host topics to it, still without a migration: `host.notify.guest_question` (`enqueueGuestQuestionNotification`, written by `submitQuestion` and `submitGuestReply` in their transaction; payload `{ v, threadId, messageId, experienceTitle }`, sent as the stoppable `GUEST_MESSAGE`) and `host.notify.new_booking` (`enqueueNewBookingNotification`, written by `confirmBookingPayment` when it confirms a booking that has a `booking_guests` row; never for `PAYMENT_REVIEW`; payload `{ v, bookingId, experienceTitle, startsAt, seats }` with the party as `seats`). Both clip the title to the row's 200 characters instead of failing the guest's transaction, and use one deduplication key per message or booking.

`0021_channel_slot_retirements.sql` tracks the old external slot left behind when a host reschedules an occurrence (#241). The desired row follows the new time; the old UTC boundaries are kept in `channel_slot_retirements` until a `SLOT_RETIREMENT` job (the existing `SET_CLOSED` executor shape) reads the slot back as closed. It adds `channel_jobs.slot_retirement_id` and extends the purpose and dispatch-assignment checks. It stores internal identifiers and times only. The runtime role needs SELECT/INSERT/UPDATE on the new table.

`0022_guest_questions.sql` additively stores 予約前の質問 (#105, #106; docs/guest-questions.md): `guest_question_threads` (one per question, scoped to a provider's product, with the guest's name, email address, topic and language), `guest_question_messages` (the guest's words or the host's English, the host's Japanese, and the email delivery state of host replies) and `guest_question_reply_tokens` (one-time reply links, SHA-256 only). `GuestQuestionRepository.questionsOpen`/`submitQuestion` take a slug that exactly one PUBLISHED product has; a repeated `clientRequestKey` is the same question, and new threads are limited to 3 per product and guest address and 30 per product an hour (`StoreRateLimitedError`). `listThreads`/`getThread`/`markThreadRead`/`reply` require a current OWNER membership as 0020 does and never return the address; `reply` is idempotent on its command UUID. The mail worker calls `claimReplyDeliveries` (`FOR UPDATE SKIP LOCKED`, a lease, at most 5 attempts) and `recordReplyDelivery`; the raw reply token exists only in the claim result. `openReplyLink`/`submitGuestReply` serve the reply page, one answer per link. Outbox events (`guest_question.received`, `guest_question.reply`) carry `{ threadId, messageId }` only. No IP addresses are stored. The runtime role needs SELECT/INSERT/UPDATE on the three tables and INSERT on `outbox_messages`.

`0023_guest_bookings.sql` additively stores 旅行者の予約 (#285): `experience_product_sale_terms` (one row per product sold to travelers: child pricing, party size, cancellation policy, NIHO-shaped booking questions with their SHA-256 fingerprint, the conditions version) and `booking_guests` (one row per booking made on this site: the guest's name, email address, optional phone, language, note, answers, party, consent versions, request fingerprint, UTM, the Stripe Checkout Session set once, `pii_erased_at`), plus a partial index of active holds per product. A trigger keeps the request immutable, the session set once and erased data erased. `GuestBookingRepository` sells a slug only when exactly one PUBLISHED product has it, it has sale terms, its price is JPY of at least ¥50 and its ID is at most 120 characters. `publicBookingTerms`/`listPublicAvailability` return NIHO's offer and availability shapes (an offer is an active schedule rule; availability is today through 89 days in Tokyo, evaluated with the host calendar's expansion and `evaluateStoredInventories` for a party of the minimum size). `startGuestBooking` checks the request in NIHO's checkout order and throws `GuestCheckoutError` with NIHO's codes; it reuses `createBookingHold`'s transaction (`lockBookingIdempotencyKey`, `materializeAndLockOccurrence`, `placeBookingHold`) with the idempotency key `guest-checkout:<productId>:<clientRequestKey>`, a 35-minute hold and an adult/child pricing snapshot whose `totalAmount` the webhook compares. Limits: 2 active holds per guest address and product, 30 per product, 5 new bookings per address and provider an hour. `attachCheckoutSession` records the session once; `eraseGuestData` blanks personal columns of bookings whose occurrence ended (the owner decided one year; the job that calls it comes with #285 slice 5). No IP addresses are stored and outbox payloads carry IDs only. The runtime role needs SELECT/INSERT/UPDATE on both tables.

`0025_provider_sale_settings.sql` additively stores what NIHO charges a provider on bookings made on this site (#285 slice 2; docs/guest-booking.md): `provider_sale_settings` (one row per provider: `support_enabled`, `platform_fee_basis_points` 1000 with support off or 1500 with it on, tied together by a CHECK, `version`, `updated_at`). `GuestBookingRepository` sells a provider's products only when this row exists (no fee is assumed) and the fee on the smallest charge is at least ¥1 and below it, as Stripe requires. `startGuestBooking` fixes `pricingSnapshot.platformFee = { supportEnabled, basisPoints, amount }` with `amount = floor(totalAmount × basisPoints / 10000)` (docs/api-contract.md states no rounding), which `experience-payments` charges as the application fee; a later change applies to later bookings only, and a replay keeps the fee it was taken at. `setProviderSaleSettings(providerId, { supportEnabled }, expectedVersion?)` writes the row (new without a version, else at that version); it takes no actor because only NIHO's server-side import or Admin may set the fee, and no route calls it yet. The runtime role needs SELECT on the table; INSERT/UPDATE belong to the import/Admin identity.

`0026_checkout_session_release.sql` widens `stripe_webhook_events.outcome` with `EXPIRED` and `IGNORED` (#285 slice 4; docs/guest-booking.md). The current writer records only the three earlier values, so it may run before the new revision. `GuestBookingRepository.releaseGuestHold` takes a Stripe Checkout Session that ended unpaid (`checkout.session.expired` / `checkout.session.async_payment_failed`): under the provider inventory lock and the event-ID lock `confirmBookingPayment` uses, a booking still `HOLD` whose `booking_guests.checkout_session_ref` is that Session and whose seller snapshot has the event's account becomes `EXPIRED` and its occurrence is recalculated; the event is recorded once with outcome `EXPIRED`, or `IGNORED` when nothing changed (a booking no longer held, another Session, none recorded). Another account is a `StoreConflictError`, an unknown booking a `StoreNotFoundError`. A payment that still arrives lands in `PAYMENT_REVIEW` through `confirmBookingPayment` without taking seats. `startGuestBooking` also marks up to 100 of the provider's lapsed holds `EXPIRED` before it counts limits and evaluates inventory (`expireLapsedHolds`, shared with `releaseExpiredHolds`); stored inventory and the hold limits already ignore a `HOLD` past `hold_expires_at`, so this is bookkeeping and no scheduled job is needed. The runtime role needs no new privilege (INSERT on `stripe_webhook_events`, UPDATE on `bookings`).

`guest-mail-outbox.ts` (#285 slice 5; docs/guest-booking.md) uses the existing `outbox_messages` without a migration for the guest's booking confirmation. `GuestMailOutbox.claimBookingConfirmations` claims only `booking.confirmed` rows of bookings that have a `booking_guests` row (`FOR UPDATE OF … SKIP LOCKED`, `available_at` as the lease, at most 8 attempts; a last attempt whose lease ran out is closed as abandoned) and returns what the email needs: the guest's address and name, the experience's title and slug, the occurrence's local date, start time and zone, the party, the total, the cancellation policy and the seller's name from the booking's snapshots. Erased guest data or a booking no longer `CONFIRMED` comes back with `email: null`. `completeBookingConfirmation` closes a row (a late report still wins); `retryBookingConfirmation` waits 2^attempts minutes (60 at most) for the claim's attempt count, or gives up at the cap. Other bookings' rows and other topics are never changed. `GuestQuestionRepository.eraseInactiveThreads` deletes questions whose last message is older than the given instant (never after now; the job passes one year), bounded per call; messages and reply links go by ON DELETE CASCADE. The runtime role needs DELETE on `guest_question_threads` (cascades run as the table owner) and SELECT/INSERT/UPDATE on `outbox_messages` as before.

`0027_guest_reviews.sql` additively stores 予約者のレビュー (#104, #108; docs/guest-reviews.md): `guest_reviews` (one per booking, `UNIQUE (provider_id, booking_id)`; the star rating, body, 良かった点 tags, the display name and origin the guest typed, a note for the host only, at most one host reply with its revision, at most one host report, and a nullable `hidden_at` that only an operator fills in the database) and `guest_review_invitations` (one-time links to write a review, SHA-256 only). A review is shown as soon as it is submitted: NIHO does not check it first (owner 2026-10-31), and a report does not hide it. A trigger keeps what the guest wrote immutable, the report set once and the first reply's date and author. `GuestReviewRepository.issueInvitation` (server side, for the thank-you mail job) needs a `CONFIRMED` booking whose occurrence ended within 30 days; `eligibility` is the hook for the attendance check that does not exist yet (TODO). `openInvitation`/`submitReview` serve the writing page, one review per link, and keep the guest's email, phone and name out of the review. `listPublishedReviews` takes a slug that exactly one PUBLISHED product has and returns the `ExperienceReviewsResponse` shape (the summary counts every shown review whatever the limit). `listReviews`/`getReview`/`saveReply`/`reportReview` require a current OWNER membership as 0020 does and never return the guest's address; `saveReply` is optimistic on `reply_revision` and idempotent on its command UUID. No IP addresses are stored and the outbox is not written. The runtime role needs SELECT/INSERT/UPDATE on both tables.

`0028_channel_ensure_occurrence.sql` adds the `ENSURE_OCCURRENCE` availability action (#241): for a listing with `can_create`, `connection_mode` `BROWSER` and a deployed adapter with `canCreate`, an OPEN occurrence first gets an `ENSURE_OCCURRENCE` job (the worker creates the GetYourGuide slot or confirms it exists) instead of `SET_OPEN`. A verified result is kept in `channel_ensured_slots` (one row per listing, occurrence, UTC start/end and mapping version, with `created` and the verifying `job_id`), and the same desired version then continues with the ordinary `SET_OPEN`; a new time or mapping has no row, so it is ensured again. `channel_job_results.ensure_created` holds the worker's `ensureCreated`, which the runtime accepts only on a VERIFIED `ENSURE_OCCURRENCE` result (the CHECK limits it to VERIFIED). The `channel_jobs.action` CHECK is rebuilt from its definition, and a second CHECK keeps the action to BROWSER availability jobs. Listings without `can_create` keep `SET_OPEN` unchanged. It stores internal identifiers and times only. The runtime role needs SELECT/INSERT/UPDATE on the new table.

`0029_booking_access.sql` additively stores 予約者の予約ページ (#285 slice 6; docs/guest-booking.md): `booking_guests.access_version` (default 1), `booking_access_grants` (one-time link grants: SHA-256 of a 32-byte token, the booking, the access version at issue, `expires_at` at most 30 days after issue, `used_at`) and `booking_sessions` (SHA-256 of a 32-byte session id, the booking, the access version, last use, idle and absolute ends, `revoked_at`), with indexes for their purge, a partial index of `booking_guests.guest_email_key` and a partial index of `outbox_messages` rows of `booking.access_link`. `GuestBookingAccess.issueBookingAccessGrant` returns a raw token (only in its result) for a guest booking that is `CONFIRMED`, `PAYMENT_REVIEW` or `CANCELLED`, not erased and less than 30 days past its end; the grant ends 30 days after issue and never past end + 30 days. `openBookingSession` marks the grant used and creates a session in one transaction (`FOR UPDATE OF` the grant; a grant opens one session), returning the raw session id. `readBookingSession(sessionId, publicBookingId)` returns the guest's view (title, slug, the occurrence snapshot's date and time, party, total, cancellation policy and its deadline, seller name, status, booked and cancelled times, the guest's own name; never the address) only for that booking, before 30 idle days and end + 30 days, while the access version matches and the data is not erased; it writes the last use at most hourly. `endBookingSession` signs one session out; `revokeBookingAccess` raises the access version (every earlier grant and session stops). `requestBookingLink({ email })` ("Find your booking") queues one `booking.access_link` outbox row (IDs only) per `CONFIRMED`/`PAYMENT_REVIEW` booking of the address (`lower`) whose experience ends in the future or ended within 30 days, at most 10 and 3 per booking an hour, under an advisory lock per address, and resolves alike whatever matched. `GuestMailOutbox.claimBookingLinks`/`completeBookingLink`/`retryBookingLink` consume that topic as the confirmations (at most 5 attempts). `purgeExpiredAccess` deletes used or expired grants and signed-out or ended sessions. The runtime role needs SELECT/INSERT/UPDATE/DELETE on both new tables.

`0030_booking_cancellations.sql` additively stores 取消と返金 (#285 slice 7; docs/guest-booking.md): who cancelled a booking and why (`bookings.cancelled_by` GUEST/HOST/SUPPORT, `cancellation_reason` from a fixed list, `cancellation_note` never shown to the guest), `booking_cancellation_commands` (one row per command UUID: actor, action, SHA-256 fingerprint of the input and the outcome, so the same command returns its first result and the same ID with other input is refused), `booking_refunds` (REQUESTED → PENDING → SUCCEEDED / FAILED, the amount, `refund_application_fee`, Stripe's refund reference; a partial unique index allows one full refund per booking that has not failed; a failed one is closed when retried or settled by hand) and `booking_cancellation_requests` (a guest's "Ask to cancel" after free cancellation; one OPEN per booking), and widens `stripe_webhook_events.outcome` with REFUND_PENDING, REFUNDED and REFUND_FAILED. `BookingCancellations` (booking-cancellations.ts) cancels under the provider inventory lock with the booking row locked: the guest through their booking-page session (`cancelAsGuest`: the snapshot's terms and deadline are read again in the transaction; CHANGED when the page showed something no longer so), the OWNER (`cancelAsHost`, `cancelSessionAsHost`, which also closes the occurrence to sale) with a full refund, and support (`cancelAsSupport` with a full or partial refund, `resolveCancellationRequest`, `resolvePaymentReview`, `retryRefund`, `closeFailedRefund`, `supportQueue`). Cancelling sets CANCELLED, returns the seats (a calendar recalculation), queues the guest's `booking.cancelled` email and, when the guest or support cancels a confirmed booking, the host's `host.notify.cancellation` push. It never calls Stripe: it returns the refunds for the caller to send, and `recordRefundSubmission` and `applyRefundEvent` move a refund only forward, write a REFUND ledger entry (negative) once Stripe accepted it and an ADJUSTMENT reversing it if it fails afterwards, and queue `booking.refunded` once it succeeded. `GuestMailOutbox.claimBookingNotices` consumes `booking.cancelled`, `booking.refunded` and `booking.cancellation_declined`. `eraseGuestData` keeps a guest whose refund is not settled or whose request is open, and blanks the cancellation note and support's message with the guest. The runtime role needs INSERT on the commands and INSERT/UPDATE on refunds and requests. `0031_refund_send_lease.sql` additively adds `booking_refunds.send_attempts` (default 0) and `send_claimed_at` for the automatic resend of refunds Stripe never accepted (#285 slice 7b): `claimRefundsToSend({ limit, olderThanSeconds, leaseSeconds })` takes REQUESTED refunds older than the grace period with `FOR UPDATE SKIP LOCKED`, holds each for the lease, counts the try, waits 2, 4, 8 … minutes (an hour at most) before the next and stops at `BOOKING_CANCELLATION_LIMITS.refundAutoSendAttempts` (8), leaving the refund REQUESTED for support's queue; `retryRefund` of a REQUESTED refund takes the same lease (without counting an attempt) and returns nothing to send while the job holds it. No new grants: the runtime already updates `booking_refunds`.

`0032_booking_messages.sql` additively stores 予約ごとのメッセージ (#285 slice 6b; docs/guest-booking.md): one thread per booking made on this site in the questions' tables. `guest_question_threads` gains a nullable `booking_id` (composite FK to `booking_guests`, ON DELETE CASCADE; UNIQUE per provider and booking) and a CHECK that a question keeps its name, address, address key, topic and request key while a booking's thread keeps none of them (they are read from `booking_guests`; `guest_language` is copied, `product_id` is the booking's). `guest_question_messages` takes the source `BOOKING_PAGE` (a guest's message on their booking page, with the page's idempotency key, as `REPLY_PAGE`); the three CHECKs are rebuilt under explicit names. `GuestBookingMessages` (booking-messages.ts) reads and writes with the booking page's session (`sessionBookingRef`, as cancelling): `readConversation` returns the guest's words and the host's English (never `body_ja` of a host message) and whether the booking takes messages (`CONFIRMED` or `PAYMENT_REVIEW` and less than 30 days past its end); `sendMessage` starts the thread with the first message under an advisory lock per booking, answers a repeated key with the same words as `repeated` (other words: `StoreConflictError`), refuses a closed booking (`BookingMessagesClosedError`) and more than 10 guest messages an hour (`StoreRateLimitedError`), and queues `guest_question.received` and `host.notify.booking_message` (`{ v, threadId, messageId, experienceTitle, startsAt, seats }`, the stoppable `GUEST_MESSAGE`). For the OWNER, `GuestQuestionRepository.listThreads`/`getThread` return the booking (`publicBookingId`, status, the snapshot's date and start, the party, `open`) and the guest's name from `booking_guests`, never the address; `listThreads` and `countThreads` take `kind` (`QUESTION`/`BOOKING`); `findBookingThread` reads a booking of the provider's (its thread or none yet); `replyToBooking` starts the thread with the host's first message; `reply` and `replyToBooking` refuse a closed booking. `claimReplyDeliveries` returns `kind: "QUESTION"` (with the reply token as before) or `kind: "BOOKING"` (the booking's guest address and name, its public ID and the snapshot's date, start and zone; no reply token), and marks FAILED a booking message whose guest record was erased. `eraseGuestData` deletes the erased bookings' threads (messages by cascade); `eraseInactiveThreads` leaves booking threads alone. No new grants: the runtime already has INSERT/UPDATE on both tables and DELETE on `guest_question_threads`.

`guest-question-translations.ts` (#285 slice 5; docs/guest-questions.md) consumes `guest_question.received` (written with every guest question and reply-page answer) without a migration. `GuestQuestionTranslations.claimTranslations` first closes a bounded batch of rows that need nothing (a Japanese thread, a message already translated, an erased thread) and rows whose last attempt's lease ran out (`abandoned`), then claims rows whose message is a guest's English with `body_ja IS NULL` (`FOR UPDATE OF o SKIP LOCKED`, `available_at` as the lease, at most 5 attempts) and returns the message text. `recordTranslation` stores the Japanese as `body_ja` only while it is still null (a late report after the lease still counts) and closes the row; `retryTranslation` waits 2^attempts minutes for the claim's attempt count or gives up at the cap. Other topics are never changed. The runtime role needs no new privilege (UPDATE on `guest_question_messages` and `outbox_messages`).

`0011_guide_draft_product_links.sql` adds ordered, article-scoped related experience selections. Publication copies the order into immutable links. Legacy sealed links keep a null order and retain the former provider/product sort; the migration does not update their rows.

The code-backed `kamakura-after-4-pm` slug is reserved at the database boundary until #189 imports that article. The import must delete its reservation and create the matching database article in one transaction before switching public readers.

The migrations do not change the current code-backed `/guides` pages. Database-backed public SSR is separately gated by `EXPERIENCE_GUIDE_PUBLIC_SOURCE=database`. HTTP invitation routes, category admin APIs, and migration of existing code-backed guides remain follow-up work.

`0010_shared_inventory.sql` はprovider所有の会場・講師・設備、商品の `SEAT` / `PRIVATE_GROUP` と資源割当、予約時のimmutable占有snapshot、providerごとのdue reconciliation tickを追加する。複合外部キーでprovider越境を拒否し、既存商品は設定がない限り席数制を維持する。ロック順とoutbox契約は [`docs/ota-inventory.md`](../../docs/ota-inventory.md) を参照する。

### 0006の配備順序

`0006` は停止を伴う移行とする。旧アプリは `schedule_occurrence_overrides` へ `CLOSE` を書くため、移行後に旧writerを使えない。また、旧readerは「日時を移動したうえで休止」を表現できない。

1. カレンダー・予約の更新受付を停止し、旧revisionとworkerの処理終了を待つ。対象表を使用中のtransactionがないことを確認する。
2. 復元確認済みのsnapshotまたはPITR復元点を確保する。顧客データをログへ出さず、旧 `CLOSE` と `RESCHEDULE` の件数を記録する。
3. migration専用権限で `0006` を適用する。旧 `CLOSE` のoccurrence ID・version・作成更新時刻が販売状態表へ引き継がれ、日時表には `RESCHEDULE` だけが残ることを確認する。
4. runtime roleへ新規3表の必要最小権限を付与する。販売状態表はSELECT/INSERT/UPDATE、command表はSELECT/INSERT、outbox表はINSERTとidentity sequenceの利用。将来のconsumerの読取・更新権限は別に設定する。
5. 対応する新revisionだけを配備し、読取・追加・日時変更・休止・再開を確認してから受付を戻す。旧新writerを同時稼働させない。

受付再開前の切戻しは、新revisionを停止し、移行前snapshotを復元して旧revisionへ戻す。新しいカレンダー更新・予約が発生した後は、アプリだけを戻してはいけない。受付を止め、新revisionで修正するか、command・outbox・日時・販売状態を照合する復旧計画を作る。後から入った予約を失うsnapshot上書きは行わない。

## Tests

`npm test` runs tests that do not require a database. When `TEST_DATABASE_URL` points to a disposable PostgreSQL database, integration tests create and drop isolated schemas. They exercise concurrent capacity enforcement; guide draft privacy, optimistic revision conflicts, atomic snapshot/link switching, immutable history, unlisted/listed reads, permission rechecks, and publication stopping; and invitation acceptance, decline, revoke, re-invitation generation, concurrent accept/revoke, current-owner/writer checks, linkable-product filtering, and public-link hiding.
