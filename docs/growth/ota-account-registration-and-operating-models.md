# 体験予約サイトの登録・運営権限とNIHOの推奨構造

調査日：2026-10-29。対象：12サービスとTripadvisorの販売経路。初回は公式の供給者向けヘルプ・約款・公開登録画面を調査し、アカウント作成、契約同意、講師招待、本番の枠変更は行っていない。その後の実機実証と採否は次節を正とする。画面内だけで確認できる権限・日本向け個別契約は未確定として残す。

同日追記：本調査後、オーナーから規約上の許可取得を確認済み。以下の「未確認」は公開資料から確認できた範囲を示すもので、許可の取り直しを設計・試作の着手条件にしない。対象アカウント・商品・操作範囲を記録し、[Studio worker詳細設計](../ota-studio-worker-design.md)の実機受入に進む。個別許可の申告と、全サイトで動作を実証したことは区別する。

関連：[カレンダー詳細設計](../../idea/active/2026-10-29-ota-calendar-operations.md)、[名義・メール・精算](niho-experience-seller-and-settlement.md)、[チャネルマネージャー調査](niho-channel-manager-feasibility.md)、[体験市場・販路調査](kamakura-experience-market-and-channels.md)。

## 1. 結論

**NIHOが会場・企画・販売・予約対応・実施手配を担う商品は④を基本にし、Airbnbは③を初期推奨とする。講師が独立して販売する商品は、正式なスタッフ招待があるサイトで③を使う。②のパスワード共有を標準化しない。**

- Airbnbには、実施を担当する共同ホストと、裏方を担当する共同ホストの区分がある。講師を掲載所有者、NIHOの個人別スタッフを裏方の共同ホストにする③なら、NIHOが講師の専門性を代わりに申告せずに日程を管理できる。
- GetYourGuideにはスタッフ別ユーザーがある。「共同ホストがないので④しかできない」は誤り。①・③に相当する運用も可能。ただしNIHOが自ら運営する商品を集約するなら④が簡単。
- Viator、KKdayにもスタッフへの権限委任がある。Klookにも体験向けの公式ガイドでサブアカウントを確認したが、資料は2021年台湾版なので現在の日本向け権限を確認する。
- じゃらんは子IDを約款に明記。ただし同一店舗内での利用許容を、そのまま外部の代行会社による利用許可へ広げない。
- アソビュー！、アクティビティジャパンは実施委託の条項がある。ainiは法人ホストと実際の実施者が別でもよいと明記。この3サイトは④の根拠が特に明瞭。
- **「NIHOが操作する権限」と「NIHOのシステムが自動で操作する許可・能力」は別判定。** 今回、全サイトで自動同期を利用できると確認できたわけではない。Airbnb以外のGoogle busy取込みも未確認。未確認は不存在や永久不採用を意味しない。

以下のサイト別節に根拠と申込入口を記載する。推奨はNIHOの今回の運用に対する判断であり、各社からNIHOへ個別承認が出たという意味ではない。

### 1.1 1時間程度の反映待ちを許容する場合の採否

同日、オーナーは予約成立から他サイトの受付停止まで1時間程度のずれを許容すると明示した。通常時の目標を**起点の変更から、対象販路での読戻し確認まで60分以内**に置く。公開APIやGoogle入力がないだけで候補から除かず、許可済みのブラウザ操作経路も使う。達成済みの時間保証ではない。

予約の定期確認はまず15分間隔を候補にし、PWAの変更は優先配送する。取得失敗を「予約なし」にせず、未確認・60分超過・認証切れをスタッフに示す。Google保存ACKだけでAirbnb反映済みにしない。実測には検知待ち、処理待ち、画面操作、サイト側の反映、最後の読戻しをすべて含める。今回の遅延許容を、既存予約の自動取消や不明な状態での再開の許可へ広げない。

以下の「有力」「候補」は公開機能からの技術的な見立てであり、NIHOによる自動運用の実証済みという意味ではない。

## 3. サイト別の登録と設定

### 3.1 Airbnb体験：③を先行、①は組織運営として検討

**登録入口**：[体験ホストになる](https://www.airbnb.com/host/experiences)、[公式の登録手順](https://www.airbnb.com/help/article/3888)。

1. 講師本人が所有・回復できるAirbnbアカウントを用意する。NIHOは原稿・写真・経歴の整理を支援する。
2. メニューのホスト登録から体験を選び、種類、内容、開催場所、実施者の経歴・専門性等を入力し審査へ提出する。
3. 公開前に本人確認を完了。内容・地域により資格、許認可、保険の提出が必要。資格証が全ジャンルで必須という意味ではない。
4. 掲載編集の `Co-hosts` からNIHOスタッフのメールを指定し、裏方を担当する役割で招待する。招待されたスタッフ自身のアカウント・本人確認が必要。
5. 日時、貸切設定、受付締切、受取方法を設定。共同ホストによるGoogle初期接続の可否は未確認なので、初回は所有者が設定する運用を想定する。

共同ホストは招待された体験の日程・カレンダー・掲載・問合せ等を扱える。当日の実施役を選ぶ場合は、その人の経験年数、研修・資格等の追加情報が必要。[体験の共同ホスト招待](https://www.airbnb.com/help/article/2685)

①も一律不可ではない。NIHOが組織として運営する実態を申告し、当日接客する実施者を指定の方式で登録する。④のように未登録の外部講師へ実施だけを任せる通常運用は採らない。共同ホストの仕組みを使わない組織運営には、追加規約§10のAirbnbによる書面承認等の例外条件がある。[体験ホスト追加規約](https://www.airbnb.com/help/article/2870)

②は利用規約のアカウント資格情報共有制限と合わない。専用Gmailを作っても解消しない。[2026年の日本を含む対象地域の利用規約・§16](https://assets.airbnb.com/help/2026_Terms_of_Service_for_Users_Outside_of_the_EEA_UK_and_Australia_-_English.pdf)

**枠管理**：公式Google連携でbusy予定を既存回の受付停止に利用できる。2026-10-29、オーナー許可済みの実体験・空き枠で、Googleのbusy→Airbnb予約不可、同じ予定をfree→元の予約可能・定員への復帰を確認し、検証予定を片付けた。NIHOからGoogleへの自動出力・貸切1組制・反映時間の一般的なp95は未検証。開催回の新規作成は別操作であり、Google busyからは作られない。[Google連携](https://www.airbnb.com/help/article/2822)、[開催回の設定](https://www.airbnb.com/help/article/2645)

### 3.2 GetYourGuide：④。独立講師の事業には③も使える

**登録入口**：[Supplier Portal](https://supplier.getyourguide.com/)、[初期登録手順](https://supply.getyourguide.support/hc/en-us/articles/13980985654941-Getting-Started-as-a-Supply-Partner)。

1. `Get Started` から連絡先・事業情報を登録し、確認メールで有効化する。
2. supplier verification、事業者情報、保険、入金・銀行情報を整える。本人・事業者確認と支払情報の完了前は商品を審査に提出できない。
3. NIHOが企画、会場、講師手配、催行責任を持つ商品として、水引・書道・料理を別商品で申請する。
4. NIHOスタッフを追加するときは、アカウント設定→Account management→Add new contact。個人別メール、ログイン許可、役割を設定し、本人が招待を有効化する。
5. 商品のAvailability & Pricingでスケジュール・価格・定員を設定する。[枠設定](https://supply.getyourguide.support/hc/en-us/articles/15882173691421-Adding-Availability-and-Pricing-to-your-product)

対象は体験を自ら運営する登録事業者・個人事業者。再販業者、集約業者、OTA等は申請対象外と明記されている。NIHOが単に他者の商品を掲載する場合は④とせず、実際の催行者のアカウントへNIHOを招待する③を使う。[申請資格](https://supply.getyourguide.support/hc/en-us/articles/13980993520925-Who-can-apply-to-be-a-Supply-Partner)

役割はAdministration、Finance、Operations、Guides。日程・商品管理を担うNIHOスタッフはOperations等の必要な役割を選ぶ。Guidesを付ければ担当商品以外が見えない、とは確認できない。共有メールは顧客連絡先に使えても、ログインユーザーは個別メールを要求される。[スタッフ・通知設定](https://supply.getyourguide.support/hc/en-us/articles/13980973710493-Updating-the-Account-Management-Section-Managing-User-Access-and-Customizing-Notifications-in-the-Supplier-Portal)

**枠管理**：Google busy／ICS入力の公式手順は未確認。supplier APIの接続制度または条件を確認した管理画面操作が候補。①・③のスタッフ制度があることだけでは無人操作の許可にならない。[接続仕様](https://integrator.getyourguide.com/documentation/overview)

なお複数アカウントの一括切替は、同一所有・法的関係等の審査を伴う別機能。独立講師全員のアカウントを自由に束ねられるとは扱わない。[Multi-login](https://supply.getyourguide.support/hc/en-us/articles/30426048876317-How-to-Use-Supplier-Multi-Login)

### 3.3 Viator／Tripadvisor：供給者登録はViatorを軸にする

**登録入口**：[Viator Supplier](https://supplier.viator.com/)、[登録・Tripadvisorとの関係](https://supplier.viator.com/sign-up-info?m=66029)。

1. Viator供給者登録でメールを確認し、会社／個人の区分を実態に合わせる。
2. Supplier Management Centerで体験を作成。商品審査の提出前に求められる本人・アカウント確認、入金設定を完了する。
3. NIHOの販売・催行責任と委託講師の体制を申告して、各体験・各オプションを登録する。委託可否の最終根拠は適用されるSupplier Agreement・商品審査。
4. Primary ContactからNIHOスタッフをsecondary userとして追加し、日程管理等を委任する。公開資料では機能の存在を確認できたが、現行の招待メニューの位置・商品限定権限は未確認。
5. 既存予約システムを接続する場合は、Account→Connectivity→Connect Nowから選択し、商品との対応を設定する。NIHO独自システムが直ちに選択肢になるわけではない。[接続手順](https://operatorresources.viator.com/connect-to-viator-through-api/)

費用面では、登録案内に**1体験あたり29米ドル相当の返金不可の提出料**と、催行済み予約へのコミッションが記載されている。無料のチャネル管理を目指す場合でも、この商品提出料は別予算になる。[公式料金FAQ](https://supplier.viator.com/sign-up-info?m=66029)

2026年8月の公式変更案内は、Primary Contactによる副ユーザーへのカレンダー・API接続等の委任と、供給者の責任を明記する。①・③の根拠になる。[Supplier Agreement変更案内](https://operatorresources.viator.com/updated-supplier-agreement-august-2026/)

**Tripadvisorを独立した予約在庫として二重登録しない。** Tripadvisorの事業者ページ・口コミ管理と、Viator経由の体験販売を区別する。掲載・販売経路ごとにURLは持つが、同じViator商品から配信される予約は一つの在庫接続として扱う。

**枠管理**：Google busy入力は未確認。Supplier Reservation System APIがあり、旅行者向けのAffiliate APIとは別。[供給者API仕様](https://docs.viator.com/supplier-api/technical/)

### 掲載可・保留・不採用の基準

ユーザーの「統合管理できないサイトには載せない」という方針に従い、**新規の共通在庫販売は次の全条件を満たしてから開始**する。既存掲載をこの調査だけで停止・削除しない。

1. **名義・実施者**：①〜④のいずれかが実際の契約・運営に適合する。
2. **NIHO権限**：必要なアカウントで対象商品・開催回を読み、開閉できる。本人しか操作できない条件なら保留。
3. **接続経路**：公式カレンダー、承認されたAPI、または適用条件上許されるブラウザ操作がある。制限に抵触する場合は許可・別経路が得られるまで保留。
4. **予約取込み**：確定、取消、日時変更を識別できる。取込み遅延・欠落を検知し、照合できる。
5. **在庫の意味**：1組2名も1組6名も同じ1組。1席だけ販売する設定で代用しない。休止した回が取消によって勝手に再開しない。
6. **現実の競合対策**：即時予約を複数サイトで同時に受ける間の競合を許容できるか確認する。厳密に二重予約ゼロが必要なら、供給時点で共通在庫をロックできる接続、またはNIHOの一元承認を経るリクエスト方式が必要。

**不採用にする具体例**：講師個人のパスワードを借りる以外にNIHOの許可された操作経路がない／委託講師の掲載が認められず適切な別方式もない／自動操作が認められず公式接続も使えない／予約の成立・取消が識別できない／必要な1組制が成立しない。

現時点では「サブホストがない」という理由だけで永久除外すべきサイトは確定していない。④なら講師のOTAログインは不要だからである。一方、**名義が成立するだけで共通在庫販売を開始しない**。未確認の接続はAdminで「保留」とする。将来、条件が確認できれば再評価する。

## 5. 共通メールを作る場合の実務

専用メールを作ることと、複数人が同じOTAパスワードを使うことは別。メールは通知整理のために使い、サイトへのアクセスは正式なスタッフ権限を優先する。

| 用途 | 推奨する扱い |
| --- | --- |
| ④ NIHOが契約者 | NIHOが管理する連絡窓口を登録。講師ごとの新Gmail作成を必須にしない |
| ③ 講師が契約者 | 講師が所有・回復できるメール。NIHOスタッフは自分のメールで招待を受ける |
| 本人確認・契約 | 本人／正式な代表者が実施。NIHOは資料・原稿・入力準備を支援 |
| 開催連絡 | 外部掲載ID→NIHO内体験→担当講師で振り分け、必要な情報だけ通知 |
| 回復・金融・認証 | 開催連絡と分離。確認コードや口座変更通知を講師全員へ転送しない |
| 退出 | 講師所有アカウントの所有権は講師へ残し、NIHOの委任を解除する |

Airbnbの経歴、GetYourGuideの事業者審査等は、専用Gmailを作っても省略できない。③でもNIHOが原稿・写真・商品設定を準備し、本人にしかできない確認だけ講師に行ってもらえば、負担はかなり集約できる。

④の講師はNIHO Experienceの自分のアカウントで日程を変更する。その後NIHOが外部サイトを操作するため、講師自身に外部サイトの招待機能がなくても構造は成立する。NIHOが外部サイトから適切な権限を受けていることが前提。

## 6. NIHO Experienceに追加する管理項目

実装仕様は[詳細設計](../../idea/active/2026-10-29-ota-calendar-operations.md)へ統合する。今回の調査から、以下を区別して保存する。

| 項目 | 内容 |
| --- | --- |
| 運営方式 | ①〜④、掲載所有者、契約上の供給者、実施担当者。表示名だけで判断しない |
| 外部権限 | 招待されたスタッフ、役割、有効期間、商品限定の可否。秘密情報は別管理 |
| 接続許容 | Google／API／ブラウザ、それぞれの適用条件・根拠・確認日・有効期限 |
| 機能 | 回作成、開放、停止、予約読取、取消読取、手動承認、貸切・1組制 |
| 停止方法 | 販売停止フラグ／在庫減算／予定ブロック等。取消で在庫復元するか |
| 導入状態 | 調査中、申請中、権限確認済み、読取検証済み、開閉検証済み、稼働、保留 |
| 停止理由 | 未承認、規約変更、契約失効、権限解除、再認証、画面変更、照合失敗 |

同じサイトでも、ある講師は③、別の商品は④となり得る。1サイト1アカウント固定にしない。1つのNIHO商品に、Airbnbは講師所有、他OTAはNIHO所有という対応も保持する。売上・契約・レビューの帰属は経路ごとに残す。

スタッフ招待が解除された場合や契約条件が変わった場合は、ブラウザにセッションが残っていてもジョブを止める。一度審査に通ったことを永久の許可として扱わない。

## 7. 実行順の提案

1. **水引1商品で名義を決める**：Airbnbは③を基本、国内は④。講師が外部ログイン不要な方式を優先する。
2. **AirbnbのGoogle経路を確認**：既存回の停止・再開、貸切、本人／共同ホストの設定権限、予約取込みを確認。
3. **国内2社目を選定**：アソビュー！／アクティビティジャパンは委託根拠が明確。じゃらんも市場との相性から候補。実アカウントを既に持つもの、許可された枠操作・通知を早く確認できるものを優先する。
4. **インバウンドの追加**：GetYourGuide／Viator／Klook／KKdayへNIHO運営商品として登録を準備。書類・商品審査と接続確認を並行できるが、確認前の共有在庫販売はしない。
5. **商品分野で追加**：国内ワークショップはaini、料理・茶はbyFood／airKitchen、選ばれた高付加価値商品はVELTRAを検討。
6. **共通在庫の開始は2販路から**：開閉・予約取消・遅延・競合・再認証の実測を通してから追加する。12サービスの一括自動対応を前提にしない。

### 各社へ確認する内容（未送信）

以下は申込時にそのまま整理して伝えられる確認事項。実際の会社情報・講師情報は非公開で扱う。

- NIHOが会場、企画、予約対応、催行責任を持ち、複数の専門講師へ実施を委託する商品を、1事業者の複数プランとして登録できるか。講師の提出・登録・通知条件は何か。
- NIHOスタッフの個別IDは発行できるか。外部の掲載代行会社も招待できるか。商品限定権限はあるか。
- NIHOの自社カレンダーと同期するため、自社管理アカウントの対象商品に限り日時の開閉を行うブラウザ自動操作を利用できるか。許可範囲・頻度・条件は何か。使える公式接続があればそちらを優先したい。
- 1回1組・人数可変の商品を扱えるか。予約、取消、日時変更の通知方法、予約ID・商品IDの取得、取消時の在庫自動復元、販売停止の保持を確認したい。

これは回答を待つ間に設計を止めるための質問集ではない。商品原稿・データモデル・読取試作の準備は進め、**各販路の販売・書込みを有効化する段階で未確認項目を解消する**。

## 8. 調査の限界と更新方法

- 供給者向け情報を優先。宿泊向けヘルプ、消費者の予約カレンダー、Affiliate／再販売API、別製品のスタッフ権限を混同しない。
- 公開ブラウザでKlookの申込フォーム、KKdayの登録入口・SCM規約、ainiの法人説明を確認した。ほかは主に公式ヘルプ・約款・募集資料を確認。ログイン後UIの全操作を実証したものではない。
- Klookのガイド・利用条件は2021年、ainiの該当ヘルプは2024年、KKday SCM規約の表示版は2024-06-21。確認日と資料の版を区別する。
- 既存アカウントの契約特約、国・商品・法人区分による違いがある。未確認の欄は、各社回答または実アカウント検証の根拠・日付とともに更新する。
- この文書は登録方式・権限の比較であり、掲載承認、API採用、全自動化の保証ではない。追加CMの月額なしでの構成は検討できても、OTA手数料・Claude実行料・保守が無料になるわけではない。
