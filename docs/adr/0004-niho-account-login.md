# ADR 0004: ログインを NIHO アカウントへ揃える（ホスト・ライター・旅行者）

- 状態: 採用（2026-11-14。方針はオーナー決定、構成はこの ADR で決めた）
- 置き換えるもの: [ADR 0003](0003-experience-independence.md) の §1 のうち「ログインはメールの使い捨てリンク」と、同 ADR の補足（2026-11-07）にあった「NIHO ログインへ戻す時期と手順は別に決める」。ADR 0003 のそれ以外（Experience の本人 ID `hst_`、販売者と受取口座、Stripe のキーと webhook、Admin の Google Workspace ログイン、NIHO の業務 API を販売の前提にしないこと）は有効のまま。
- 関連: Epic [#591](https://github.com/niho-life/niho-experience/issues/591)（子 #592〜#598）、#481、#456、#477、niho-coliving/niho-app#20305・#20306・#20307・#19917・#19943

## 背景

- ADR 0003 で、ホストのログインを Experience 自前のメールのリンクにした。NIHO 本番に Host v1 の入口が無く（`/api/experience-host/identity` が 404）、本番の公開が niho-app の配備を待つ状態だったため。同日、オーナーは「ホストのログインの本来の形は NIHO ログイン。メールのリンクは一時的」と補足した。
- その理由は解消した。niho-coliving/niho-app#19917 は 2026-11-11 に close し、本番の `identity` は有効（認証なしで 401）。`APP_CONNECT_WEB_ORIGINS` に Experience の origin が入っている。
- メールのリンクの実害が出ている。
  - iOS のホーム画面アプリでログインが完結しない（リンクは Safari で開き、アプリと cookie を共有しない）。
  - メールのアプリが自分のブラウザでリンクを開くと、別のブラウザ扱いで使えない。
  - ログインがメール job と SMTP に依存する。
  - OWNER 以外のライター（#481）は NIHO のライター権限で入るので、NIHO の本人が要る。
- 旧方式（NIHO の接続トークンを cookie に封入してセッションにする）へは戻さない。
  - DB は `hst_` と `sel_` を前提にしている（membership・販売者・同意・チーム・push・`*_niho_user_id` 列）。
  - 公開版と写真の作成者は trigger で不変なので、ID を一括で置き換えられない（#477 のレビュー）。
  - 回転する refresh token を、ブラウザとホーム画面アプリの複製 cookie で別々に更新すると、接続ごと失効する（`docs/host-pwa.md`）。
- 本番のホストは少なく（2026-11-07 時点で OWNER 1 名）、外部の提供者を受け入れる前で、移行が一番安い。

## 決定

### 1. 人の ID は NIHO アカウント

- ホスト・ライター・旅行者とも、人の ID は NIHO アカウント（NIHO の `User.id`）。NIHO アプリ・photo・docs と共通。
- ログインの方法（LINE・Google・Apple・メールとパスワード）は NIHO 側の「鍵」で、Experience は方法を区別しない。
- 優先する方法は、ホスト＝LINE、旅行者＝Google（オーナー決定 2026-11-14）。LINE は 1 アカウント 1 名を担保しやすい（niho-app の `email-password-login.md` の優先順位 LINE > Apple/Google > メール と同じ向き）。優先は並び順で示し、ほかの方法も使える（LINE を必須にしない）。
  - ホストは、運営が登録した本人に結び付く（3）ので、別の方法で別の NIHO アカウントを作っても入れない。重複は構造上起きず、並び順で足りる。

### 2. NIHO は本人確認だけに使う

- ログインは NIHO の app-connect の Web の接続先 `niho-experience`（PKCE S256・一度きりのコード）を使う。
- 戻ったら、サーバーが code を交換し、`GET /api/experience-host/identity` で NIHO user ID と `ACTIVE` を確かめ、その接続をすぐ解除する（`DELETE /api/auth/app-connections/{id}`）。
- NIHO のアクセストークンと refresh token は、セッションにもサーバーにも残さない。セッションの間は NIHO を呼ばない。
- NIHO の機能を使う連携（記事のライター権限など）は、ユーザーの bearer ではなく、Experience のサービス ID トークンと NIHO user ID のサーバー間の契約で呼ぶ（例: `POST /api/internal/editor-article-authority/check`）。

### 3. `hst_` を残し、NIHO user ID を結び付ける

- Experience の本人 ID `hst_`（ホストアカウント）はそのまま。権限（`provider_memberships`）、販売者、同意、記事・公開版・写真の作成者は変えない。
- 結び付けの表 `host_account_identities` を足す（#593）。
  - 1 つの `hst_` に有効な NIHO user ID は 1 つ。同じ NIHO user ID は別の `hst_` に付けられない。
  - 結び付けは、招待リンク（#596）、設定での結び付け（直近のログインを要求、#595）、運営の登録のどれか。経路を記録する。
  - 結び付けと解除は監査ログに残す。NIHO user ID は監査以外に出さない。
- ホストとしてログインできるのは、結び付いた `hst_` が `ACTIVE` のときだけ。NIHO にアカウントがあるだけではホストにならない。
- メールのアドレスでの自動の結び付けはしない（NIHO もメール一致で統合しない）。

### 4. セッションは Experience のもの

- セッションは今の Experience 自前のもの（`host_sessions`、cookie `__Host-niho_host_account_session`・Path=/）。`/host` と `/write` の両方に届く。
- `authenticated_at` には、NIHO が本人を確かめた時刻（`auth_time`）を入れる。
- アイドル 14 日・最長 30 日・失効・push の扱いは今と同じ。
- ホーム画面アプリでも、NIHO の往復をアプリの中で完結させる（#594 で実機確認）。セッションは回転する token を持たないので、複製された cookie で失効しない。

### 5. 入口と取り違え

- ホストの入口（`/host/auth/sign-in`）は、見出しとボタン 1 つ（「NIHO アカウントでログイン」）だけ。補足文・メールのリンク・「体験の提供について」は載せない。
- NIHO 側は、対象（ホスト／旅行者）に合わせてログインの方法を並べ、前回使った方法に印を付ける（niho-app#20306）。接続の確認画面には、いまのアカウント（ログイン方法・メールの一部）を出す。今回のログインで新しく作られたアカウントなら、「別のアカウントで続ける」を主操作にする（niho-app#20305）。
- 結び付いていない NIHO アカウントで入ったら、Experience は「このアカウントは、ホストに登録されていません」と、原因の見当（別の方法で入っていないか）と「別の方法でやり直す」を出す。Experience のデータには触れず、ほかのアカウントの有無も示さない。

### 6. 直近のログイン

- 受取口座の同意と取り消し、Stripe ダッシュボードを開く、公開の 3 つは、今と同じく 30 分以内のログインを要求する。
- 判定は `authenticated_at`（NIHO の `auth_time`）で行う。古いときは NIHO で再ログインさせる（再認証の指定は niho-app#20305）。
- 再認証の指定が NIHO 本番に入るまで、本番で NIHO ログインを有効にしない。

### 7. ライター（提供者なし）

- 体験の OWNER でないライター（#481）は、`/write` に初めて NIHO ログインで入り、NIHO のライター権限を確かめられたときに、メールの無い `hst_` を作って結び付ける。
- そのため、`host_accounts.email` を NULL 可にする。メールの無いアカウントには、メールのリンクを送らない。
- ライター権限は、保存・公開のたびに NIHO へサーバー間で確かめる（#481）。

### 8. 旅行者

- 旅行者のアカウントは任意で、ゲスト予約と予約ごとのセッション（`docs/guest-booking.md`）は残す。オーナー決定 2026-10-27「旅行者のアカウントは作らない」を、この ADR で見直す。
- 旅行者には NIHO の名前を出さない。
  - 入口は Google / Apple / LINE の方法別ボタン。押すと各社の画面へ直行し、戻ったときに NIHO アカウントができている。
  - すでに NIHO アカウントを持つ人のために、一番下に小さく「NIHO アカウントでログイン」を置く。こちらは NIHO のログイン画面と接続確認を通る。
- 旅行者のアカウントは、ホストアカウント（`hst_`）とは別の表と別の cookie にする（ホストの権限と混ぜない）。予約・メッセージとの結び付けは #597 で決める。
- NIHO 側で必要なのは、方法の指定つきの直接開始と、旅行者向けの接続の確認画面の省略（niho-app#20307）。省略はセキュリティの確認とオーナーの判断を経てから有効にする。
- 旅行者のログインは Experience のサーバー経由で NIHO の `exchange` を呼ぶ。今の IP 単位の上限（`exchange` は 10 分で 20 回、niho-app の `experience-site-integration.md` §16.4）では足りなくなるので、旅行者のログインを開く前に、Experience のサーバーを識別して上限を分ける。

### 9. メールのリンク

- メールのリンクのログインは、移行が終わるまでのフォールバックとして route を残し、画面には出さない。
- 移行後に撤去するか、運営の救済手段として残すかは #598 で決める。

## 保存の約束（履歴を変えない）

- 記事 ID・slug・公開版・写真の作成者・同意の履歴は、ログインの方式を変えても書き換えない。
- 認証に使う外部の ID（NIHO user ID）は、`host_account_identities` で `hst_` に対応付ける。過去の操作者 ID（`hst_`）はそのまま残す。
- 受入の基準: メールのリンクで作った記事と写真を、NIHO ログインに切り替えた後も、同じ記事として編集・更新公開できる。URL・写真・公開履歴は変わらない（#596）。

## セキュリティ

- NIHO の接続は PKCE S256・state・戻り先の完全一致・5 分 1 回限りのコード（NIHO の既存の仕組み）。Experience は verifier と state を 10 分の暗号化 cookie に置く。
- NIHO のトークンをブラウザにも保存領域にも置かない。交換の直後に接続を解除する。
- `identity` で `ACTIVE` を確かめられないとき（停止・削除・NIHO の障害）は、セッションを作らない。NIHO の障害は「確認できません」と示し、「権限がありません」と断定しない。
- 結び付けは 1 対 1 で、別の `hst_` への付け替えは、解除してからでないとできない。解除で入る手段が無くなるときは拒否する。
- 招待リンク（#596）は 32 バイトの乱数で、保存は SHA-256 だけ。1 回限り・期限付き。
- 未登録の案内は、そのログインのアカウントのことだけを示し、他のアカウントの有無を示さない。

## 移行

1. #593（結び付けの表）と NIHO 側（niho-app#20305・#20306）を並行して進める。
2. #594（`/host` のログイン）を新しい flag（`EXPERIENCE_HOST_NIHO_LOGIN_ENABLED`、既定 OFF）の裏に入れる。続けて #595（設定）、#596（招待と既存 OWNER の移行）。
3. staging で受入する（ログイン・未登録・再認証・招待・ホーム画面アプリ・既存の記事の継続）。
4. 本番で flag を ON にし、既存の OWNER を招待リンクで移行する。
5. 旅行者（#597）は niho-app#20307 と上限の分離の後。
6. 受入の後、メールのリンクの扱いと旧 NIHO トークン方式のコードを整理する（#598）。

## 結果

- NIHO に依存するのは、ログインの瞬間だけになる。NIHO が止まっている間は新しいログインができないが、既存のセッション（最長 30 日）と販売は止まらない。
- ログインがメール job と SMTP に依存しなくなる。ホーム画面アプリで完結する。
- 人の ID が NIHO 全体で 1 つになり、ライターの権限など NIHO の機能とつながる。
- 方法を取り違えると空の NIHO アカウントができる。これは NIHO の確認画面とログイン画面（niho-app#20305・#20306）と、Experience の未登録の案内で気づけるようにする。統合はしない。
