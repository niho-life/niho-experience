# Experience sales cutover

This cutover moves one product at a time. The Experience database is the new checkout gate; a missing or incomplete cutover record means Experience checkout refuses that product. Recording the legacy-stop row also removes that product from the legacy Experience checkout path, even before its first Experience publication. `ExperienceSalesCutover` and `ExperienceProductMediaImport` are operator-only modules. The web runtime has read access to cutover and imported inventory, not write access.

## Order

1. Stop the matching product's sale in NIHO. Verify no new NIHO checkout can create a hold.
2. Wait until every pre-stop hold is confirmed, expired, or reconciled. A still-open hold blocks progression.
3. Export the matching product, public sale terms, and future schedule rules. The export must use the product's stable source IDs and account references returned by the trusted NIHO migration source; do not make up seller or Connect references. Run `cutover-product.mjs import-product <manifest.json> --legacy-sale-stopped --yes`. That transaction imports the product, terms and schedule rules and creates the cutover row together. It has no partial PUBLISHED-product state and rejects a duplicate import.
4. Export only the confirmed future seat facts needed by Experience: mapped `occurrenceId`, seat count, source revision, and a keyed SHA-256 reservation reference. Do not export guest name, email, phone, answers, raw booking ID, or raw source account ID. Importing the inventory materializes each future occurrence from its stored Experience schedule rule in the same transaction.
5. Copy public photos to the Experience public-media bucket as normalized JPEGs. Confirm the provider's public-use rights, preserve contiguous zero-based ordering and alt text/credit, then register asset metadata with `cutover-product.mjs register-media <manifest.json> --yes`. The public API never returns bucket/object keys.
6. Record that holds are drained, import the confirmed inventory manifest, publish through the OWNER boundary, then enable Experience checkout. `experience-sales-started-at` is the last gate.

`scripts/experience/cutover-product.mjs` imports the product/schedule bundle, registers already-copied media, and advances or reads the cutover record. Product import requires the operator's explicit `--legacy-sale-stopped` assertion as well as `--yes`. Its JSON accepts only `providerId`, `product`, `saleTerms`, and `scheduleRules`; top-level product, sale-term, and rule fields are allowlisted, then validated by the same store/domain validators as normal writes. Media and reservation import are one-time operations. Cutover-state mutations require `--yes` and the current `version`. The confirmed-inventory JSON accepts only `providerId`, `productId`, and `reservations`; each reservation accepts only `sourceRefHash`, `sourceRevision`, `occurrenceId`, and `seats`. The manifest hash is computed from normalized rows. A rerun after a timeout starts with `status` and uses the returned version; an old version is rejected.

Imported future seats are immutable reservation inventory and are counted together with Experience bookings and other external reservations under the same inventory lock. This is conservative: the imported seats are not freed by editing the product or changing its schedule. Rollback calls `stop-experience` first. It never reopens NIHO sale automatically; reconcile Experience holds before an operator separately reopens the legacy channel.

The operator must use a verified old-sale stop and a complete hold/reservation export as the source evidence. This repository cannot query niho-app's private database or prove an operator's external stop from the Experience database alone. The product-import manifest must come from the trusted A migration contract; current A host APIs do not yet provide the authenticated stable user ID and seller/Connect mapping required for OWNER publication, so the Experience host BFF stays closed until that contract is added.

## Unresolved booking conditions

The prior `FREE_UNTIL_24H` / `FREE_UNTIL_48H` / `NONE` policies and `minimumChargeYen=50` remain the existing guest-checkout contract. The publication and checkout DTOs now support explicit cancellation window/refund ratio, private-group booking, a minimum adult-price-equivalent chargeable party size, and an operations-only minimum attendance target. Existing policy values migrate exactly; any new product value still requires an explicit seller/operator choice. The host session report counts confirmed participants toward minimum attendance and does not make cancellation or refund decisions automatically. `minimumChargeYen` is not a seller's minimum price.
