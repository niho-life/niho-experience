# ホストとライターのガイド記事作成画面

作成日：2026-10-29。状態：仕様確定・分割実装中。Epic [#185](https://github.com/niho-life/niho-experience/issues/185)。関連：[#147](https://github.com/niho-life/niho-experience/issues/147)、[#145](https://github.com/niho-life/niho-experience/issues/145)、[#16](https://github.com/niho-life/niho-experience/issues/16)。

## Goal

NIHO アカウントを持つ体験ホストと、記事を書く権限を付与されたライターが、鎌倉の一次情報を使った記事を画面で作成・保存・確認し、自分で公開・更新・公開停止できるようにする。公開記事から体験へ、対象体験から記事へ移動できる。初期版の旅行者向け記事は英語を先行する。

オーナー回答：初期版からホスト・ライターが本人の操作で公開できる。公開時に運営の毎回の承認は置かない。編集は主に PC のブラウザで行う。ライターは自分の記事だけを作成・公開する。

## Current system

- `/guides` と `/guides/{slug}` に SSR、著者・日付、本文、関連記事、体験 CTA、構造化データ、sitemap がある（`apps/web/src/app/(site)/guides/`、`apps/web/src/lib/guide-registry.ts`）。体験詳細からの記事リンクもある。
- 公開記事の正本は現在 `apps/web/src/content/guides/index.ts` の `PUBLISHED_GUIDES`。現時点では #184 の `kamakura-after-4-pm` が非掲載・直接 URL の公開記事として 1 本あり、一覧には出ない。下書きは非公開台帳で作り、mock でプレビューする（`docs/content/guides.md`）。記事公開にはコード化、PR、配備が要る。
- 2026-10-26 の `docs/adr/0002-guide-content.md` は少人数の Git 編集を前提にこの方式を採用し、非エンジニアが直接公開するときに再検討すると定めている。今回がその再検討の契機。2026-10-27 の `docs/adr/0002-experience-domain-ownership.md` に従い、記事の正本と権限は experience 側、NIHO はアカウントの正本とする。
- `/host` は NIHO の一度きりのコードでログインし、セッション cookie の Path は `/host`。提供者の選択は `?providerId=`。提供者の権限と一般の「記事ライター」権限は別に扱う必要がある。ホスト PWA の scope も `/host/`。
- 現行の `Guide` と Markdown サブセットの検証・描画は再利用できる。ただし `relatedExperienceSlugs` が 2〜3 件必須という公開検証は、体験を紹介しない地域記事も書けるよう 0〜3 件へ変更する必要がある。

## User journey

1. ホストは `/host` の「記事を書く」から、ライターは編集画面の入口から NIHO アカウントで入る。提供者のないライターにも編集画面を開ける。両方の権限がある人は、記事の公開主体を「提供者」または「個人ライター」から選ぶ。
2. `/editor/guides` に自分が管理できる下書き・公開記事を表示し、`/editor/guides/new` で新規作成する。作成時に題名の仮入力だけで非公開の下書きを保存できる。
3. 本文、概要、カテゴリ、写真と代替文・クレジット、著者の公開表示、事実確認日、関連体験を編集する。本文は見出し・段落・箇条書き・太字・斜体・リンクをその場で整形する。行頭の `## ` は入力中に見出しへ変換する。内部では既存の安全な Markdown へ変換し、書き手に Markdown やコードを要求しない。保存状態と競合を明示する。FAQ・表・囲みは初期版の必須入力にせず、既存公開記事の描画は維持する。
4. 認証済みの本人だけが公開ページと同じ描画のプレビューを見る。公開ボタンの前に、未確認記号、必須項目、写真の権利・alt、危険なリンク、存在しない関連記事を検査する。検査を通った本人が公開する。
5. 公開後は `/guides/{slug}` が SSR され、一覧・sitemap・体験詳細の関連記事に反映する。更新編集中も旧公開版を表示し、「変更を公開」で新版へ切り替える。公開停止で検索対象から外す。

失敗時：保存失敗は入力を保持して再試行する。同時編集は版番号の競合として示し、上書きしない。権限剥奪後は保存・公開を拒否する。非公開・販売停止の体験は CTA や相互リンクに出さない。画像公開に必要な権利が未確認なら公開を止める。

画面は「記事一覧 → 本文を直接編集 → 公開前の確認 → 公開」を主導線とする。PC は本文が公開ページに近い見え方の中央レール、右レールにカテゴリ・slug・説明・サムネイル・関連体験を置く。編集中の本文に独立した常時プレビューを並べず、公開ページ全体の確認だけ別の切替表示にする。上部には状態・保存・プレビュー・公開の操作だけを置く。説明文や工程名を重ねず、ラベルと配置で使い方が分かるようにする。公開前の不足項目は該当欄へ戻れる。モバイルは編集・設定を切替表示とし、初期版の主対象は PC ブラウザ。キーボード操作、見出し構造、写真の代替文を初期受入に含める。

## Options

| 案 | UX | 実装・運用 |
| --- | --- | --- |
| A. `/host/{hostname}/article/new` とホスト記事専用 CMS | ホストには分かりやすい | ライターに提供者の登録を強いる。提供者変更や複数提供者で URL が不安定。別の編集画面を後で作る可能性が高い |
| B. `/editor/guides/new` の共通編集画面、公開主体を権限で選ぶ | ホストとライターが同じ作業を同じ画面で行える。公開の `/guides` と概念が一致 | `/host` の cookie と PWA scope を越えるため、編集用ログインの導線が必要 |
| C. Git の公開手順を維持し、下書き入力だけ画面化 | 非公開の原稿入力は楽になる | ライター本人が公開できず、今回の目的を満たさない |

**推奨：B。** URL は `experience.niho.life/editor/guides/new`、公開 URL は既存の `/guides/{slug}`。画面名は日本語で「記事」。`/host` からは同じ編集画面へ導く。`hostname` は認可の根拠にせず、記事の `providerId` をサーバーで確定する。公開 URL と編集 URL を分け、編集画面全体を `noindex`・`no-store` とする。

## 権限とデータ境界の提案

| 権限 | 作成・編集・公開の範囲 | 体験との紐づけ |
| --- | --- | --- |
| 体験の編集権限を持つホスト | `OWNER`・`EDITOR` は自分で作成した提供者の記事を編集・公開できる。複数所属なら記事ごとに公開主体を選ぶ。`VIEWER` には許可しない | 自分の提供者の公開体験は記事↔体験を相互表示できる |
| 招待されたライター | 自分が作成した記事だけを編集・公開・公開停止できる。提供者所属や Stripe 口座は不要 | 自分が承諾した、その提供者の**記事連携メンバー**に限り、提供者の公開体験を選べる |
| NIHO 編集担当 | 権限付与・停止、記事の訂正・公開停止、監査 | 必要な記事・体験を管理する |

`provider_memberships` の `EDITOR`、サイト全体の `WRITER`、提供者ごとの記事連携メンバーは別権限とする。記事連携メンバーは**記事と体験の関連付けだけ**を許可し、既存の `COHOST` 相当の体験編集・予約・顧客情報・売上権限を渡さない（オーナー確認済み）。ユーザー ID は NIHO の安定 ID を参照するが、記事本文・下書き・権限・公開履歴は experience DB に保存する。著者表示は本人が確認した実名・役割・紹介文とし、アカウント ID、内部権限、非公開のプロフィールは出さない。著者と編集操作をした人、公開主体は別フィールドにする。作成者以外のホスト・ライターによる記事変更は初期版で許可せず、運営の訂正・公開停止だけを例外とする。

記事は不変 ID、公開 slug、公開主体、著者、下書き版、公開版、公開日時、更新日時、事実確認日、公開状態を持つ。記事と体験は ID で関連付け、公開時に相手が公開中かを確認する。本文に任意の体験 URL を書けても、体験詳細への関連記事表示は権限のある関連付けだけにする。写真は下書き中は非公開保管し、公開時に権利を確認した素材だけを公開配信する。下書き、限定プレビュー、アップロード URL を sitemap・公開 API・ログ・計測へ出さない。

最初の実装では既存の `Guide` と安全な本文パーサーを表示形式として使い、DB の公開版から読み込む。`PUBLISHED_GUIDES` は切替中の互換入口として扱い、二重の正本にしない。#184 の非掲載記事は #189 の公開読取切替時に DB の `UNLISTED` 公開版へ移し、slug の予約を同一トランザクションで引き継ぐ。非公開台帳の #147 原稿は本人が画面へ取り込むか、許可された担当者が移す。原稿は公開リポや合成 fixture に入れない。

## 認証と公開の実装境界

- `/editor` に独立した NIHO ログイン入口と Path `/editor` の HttpOnly セッションを設ける。ホスト用 cookie（Path `/host`）はブラウザから `/editor` へ送られない。ホスト用の回転 refresh token を別 cookie に複製すると競合するため、同じ token を二つのセッションで別々に更新しない。初期版は編集用の独立した NIHO 接続で安全に始め、ホスト画面からはログイン後の編集先へ案内する。ログイン回数を減らす手渡しは、サーバー側に単一のセッション正本と更新ロックを設けてから検討する。
- 認可は画面だけでなく記事 API の各操作で、NIHO アカウントの有効性、experience 側の現在の権限、記事の公開主体を確認する。編集・公開・公開停止は同一 origin、CSRF 対策、版番号条件、監査記録つきで行う。
- ホスト PWA は `/host/` のみを扱う。`/editor` は初期版では通常のブラウザ画面として開く。記事の執筆と公開の受入対象は PC ブラウザであり、PWA 内での編集完結は初期条件にしない（オーナー確認済み）。
- 新しい記事 API は experience 側の v1 として設計する。NIHO の既存ホスト API 版に記事操作を足さない。API と DB の互換的な追加を先に配備し、公開 SSR・sitemap の切替は後に行う。

## 初期版の受入条件

1. 提供者のないライターと編集権限のあるホストが、それぞれ本人の NIHO アカウントで PC ブラウザから下書き・プレビュー・公開・更新・公開停止できる。ライターは他人の記事・下書きを編集できず、公開されていない他人の下書きも見えない。
2. 公開操作の直前に本文・著者・権利・関連リンクをサーバーが検証し、`[CONFIRM]` と仮素材を含む記事は公開できない。
3. 公開記事だけが SSR、`/guides`、sitemap、構造化データ、体験詳細の関連枠へ出る。下書き・編集中の新版は認証済みの本人以外に見えない。
4. 記事から体験へ、権限のある関連付けでは体験から記事へ移動できる。未掲載の体験では相互リンクを隠す。
5. 同時編集、権限剥奪、アップロード失敗、公開停止の各ケースで安全に失敗し、公開済みの版は勝手に変わらない。

## Open questions

- **決定済み**：ホスト・ライター本人に公開権限を渡す。公開時の必須検査と事後の訂正・公開停止は残す。
- **決定済み**：PC ブラウザでの編集を初期版の主対象とし、ホスト PWA からの入口はブラウザで開く。
- **決定済み**：ライターは自分が作成した記事だけを編集・公開できる。他人の記事の訂正は編集担当に限定する。
- **提案**：experience DB の `OWNER` と `EDITOR` に記事の作成・公開を許可し、`VIEWER` には許可しない。旧 NIHO API の `COHOST` は移行時に役割対応を確認する。
- **決定済み**：招待ライターが体験へ記事を関連付けられるのは、その提供者の記事連携メンバーとして承諾済みの間だけ。体験・予約を操作する既存サブホスト権限は付けない。ホストは自分の提供者の体験だけを関連付けられる。

## 2026-10-29 追加のオーナー決定と設計

- 記事を書く入口はホスト URL 配下へ固定せず、`/editor/guides` と `/editor/guides/new` にする。ホスト・ライターが同じ編集画面を使う。NIHO アプリや niho-web の共通点を無理に合成せず、本文を直接編集する中央レールと必要なページ設定だけを置く。
- NIHO 管理者は **niho アプリの管理画面**からライターを NIHO user ID またはメールアドレスで招待する（オーナー確認済み）。メール照合・検証済みメール・未登録者の期限付き招待・配送・承諾は NIHO 側が正本。Experience はメールを保存せず、承諾済みの NIHO user ID と writer grant だけを持つ。既登録・未登録を UI 応答で区別せず、NIHO 側の本人確認・配送・照合契約を限定 API として別 Issue で確定する。
- 体験ホストはライターを、自分の提供者の「記事連携メンバー」へ招待する。ライター本人の承諾を経て有効化し、取り消しを即時反映する。既存の運営チームの `COHOST` や `EDITOR` を流用しない。
- カテゴリは管理者が選択肢を管理する。初期候補は「食」「文化」「旅」で、公開名は旅行者向け英語を先行する。記事は公開時に有効なカテゴリを一つ選ぶ。現在の `pillar` 固定値は既存ガイドの互換表現として保持し、段階的にカテゴリへ移す。
- 記事と体験の関連は同一レコードから双方向に表示する。公開中の記事・公開中の体験だけを双方の末尾へ出し、権限が失われた関連付けは即時に非表示にする。体験カードに価格・残席などの固定コピーを書かず、公開カタログの現在値を使う。
- 未公開原稿・画像は公開 Git、公開 API、検索、計測、ログに出さない。画像アップロードは非公開保管→権利・alt 確認→公開版で配信する。公開ボタン直前にサーバーで本人権限、カテゴリ、本文、slug、写真、関連先を再検査する。
- `/editor` は `/host` と別の NIHO OAuth client/audience、別の回転 refresh token、Path `/editor` の cookie にする。NIHO 側に同時接続可否と別 client を先行契約する。単一 token を二つの cookie に複製しない。
- 記事の状態は非公開下書き、本人限定プレビュー、公開版、非掲載・noindex の公開版、公開停止を区別する。#184 の非掲載記事は URL を知る誰でも読めるため、下書きの代わりに使わない。
- 編集器の正本は限定 AST（段落、H2/H3、リスト、太字、斜体、リンク）。保存時に安全な Markdown を一方向に生成し、サーバーで再パースする。貼り付けは初期版ではプレーンテキスト。既存記事の表・囲み・FAQ は表示できても、初期 CMS で編集対象にしない。消さずに読み取り互換として扱う。
- 公開読取は記事・体験の現在の公開状態と、リンク作成者の現在の権限を毎回確認する。権限失効後は記事本文を消さず、両側の関連リンクだけ即時に隠す。cache 無効化も権限変更に含める。
- production の公開ソースで静的 `PUBLISHED_GUIDES` と DB 公開版を union しない。公開読取の切替 PR で一覧・詳細・体験詳細・sitemap を同じ DB 読取モデルへ一括変更する。#184 の記事は非掲載状態の公開版として移す。

## 分割実装の提案

1. Epic と依存 Issue を作る。#147 の記事原稿と、現在の #184 の非掲載記事 PR には手を入れない。
2. 認証・招待・カテゴリ・記事・体験関連の DB/API 契約を実装する。公開 API の形が固まるまで既存 `/guides` は従来の正本を使う。
3. 本文一体型の編集画面と下書き保存・公開操作を実装する。初期版は AI 編集を含めない。
4. 公開版から SSR・sitemap・記事／体験の相互表示へ切り替える。既存の静的公開ガイドと二重表示しない。権限境界、公開前後、検索、写真の検証を合成データで受け入れる。
