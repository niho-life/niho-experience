# 地域の協力者が参加するための実装計画

作成日：2026-10-24。更新日：2026-10-26。状態：実装提案。

[鎌倉の体験をみんなで育てる事業方針](../../docs/growth/community-led-strategy.md)を、店舗の参加、掲載準備、地域の協力、予約運営へつなげる。まず既存の予約基盤と代理での掲載準備を整え、少数の協力を運用で試してから必要な機能を追加する。本計画は機能・料金・報酬条件の適用決定や、実運用の受入完了を意味しない。

## 目的と参加者

体験を持つ人がヘルプを出し、地域の人が得意なことで参加し、仕事と対価に合意して、旅行者へ良い体験を届けられるようにする。NIHOは参加・協力・運営の共通の仕組みを担う。

| 参加者 | 主な関わり方 |
| --- | --- |
| コンテンツ提供者 | 体験の内容・販売条件を確認し、当日の体験を提供する |
| プロデューサー | 写真・原稿・体験の構成や見せ方を改善する |
| リファラー・エバンジェリスト | 関係者へ紹介し、街と旅行者の接点を増やす |
| トランスレータ | 合意した開催回で通訳を担当する |
| NIHO事務局 | 掲載準備の進行、参加者の調整、必要な予約支援を担う |

一人が複数の役割を持てる。協力するだけの人に、店舗登録や販売者用の決済口座を要求しない。報酬の受取に必要な手続きは、採用する支払方法に応じて別途定義する。

## 現状と残る差分

- Admin予約操作、Host支援設定、料金・精算表示の画面と選別契約はmainへ入っている。各仕様には配備・受入前の制約が残る。画面のマージを実APIの接続・有効化・三者の通し受入の完了と扱わず、[#121](https://github.com/niho-life/niho-experience/issues/121)、[#128](https://github.com/niho-life/niho-experience/issues/128)、[#130](https://github.com/niho-life/niho-experience/issues/130)で残作業を確認する。
- 日本語原稿と英語の確定、レビュー返信、通知・カレンダー設定の[PR #116](https://github.com/niho-life/niho-experience/pull/116)はマージ済み。合成プレビューと実保存の接続は区別する。
- 提供者の既存権限はOWNER / EDITOR。地域の協力者向けプロフィール、ヘルプ募集、提案・採用、商品単位の協力合意・報酬確認は追加設計が必要。
- 既存の提供者編集や予約の支援に加えて、本人未登録の掲載準備から代表者の受入・販売開始へ進む導線が必要。[体験ページ編集のIssue #89](https://github.com/niho-life/niho-experience/issues/89)だけでこの一連の導線を実装済みとは扱わない。
- 流入UTMと計測方針はある。紹介者への報酬の権利を確定する記録は別途設計する。

現在の料金・支援設定は[Host本人のNIHOサポート設定](../../docs/host-support-settings.md)と[支援のEpic #117](https://github.com/niho-life/niho-experience/issues/117)を参照する。この計画では新しい料率や自動分配を決定しない。

## 店舗の参加と代理での掲載準備

店舗が完成イメージと自分の負担・受取条件を理解してから参加を決められるようにする。店舗を販売者とする既存のDirect決済を前提に、NIHOや協力者が準備・運営を担える形を提案する。

1. **掲載相談**：店舗の意向、体験の概要、写真・原稿などの利用範囲を確認する。
2. **非公開の掲載準備**：NIHOが写真、日英原稿、価格案、開催条件、運営分担を用意する。店舗本人の登録前でも準備できる。
3. **内容確認**：店舗へ限定したプレビューを送り、「掲載内容」「販売条件」「運営分担」を確認してもらう。主操作は「この内容で進める」、副操作は「修正を依頼する」。
4. **代表者の受入**：既存のNIHO認証を使い、正しい店舗と代表者を結び付ける。初めての人には対象のページを保持したまま登録を案内する。
5. **販売準備**：販売条件と支援範囲に同意し、販売者本人に必要な決済・売上受取の手続きを進める。残っている作業と中断後の再開先を示す。
6. **販売開始**：承認した掲載内容・条件と、共通APIが返す販売可能状態を照合して公開する。
7. **継続支援**：店舗は受入可否の回答と体験提供を中心に担当し、合意した範囲でNIHOや協力者が編集・連絡・手配を続ける。

プレビューの閲覧は原則ログイン不要の限定リンクとし、原稿確認に不要な個人情報を含めない。リンクを知っているだけでは正式な承認・管理権限の受入を成立させない。失効・撤回時の扱いも設計する。

素材の利用許諾、掲載内容の確認、販売条件への同意、予約対応を任せる許可は、何に同意したか分かるように記録する。承認した内容の版を固定し、価格・取消条件等の重要な変更には再確認を求める。NIHOスタッフを店舗本人や同意者として仮登録しない。

初期版では販売準備が済むまで非公開確認を基本とする。事前の需要確認として「開催の相談」を公開する場合は、料金請求・席確保・予約確定を伴わない別の導線として設計する。

事務局には「掲載準備」の一覧を置き、店舗、担当者、次の作業、誰の返答待ちかを示す。代表者の受入、内容の承認、決済準備、公開状態、支援範囲は独立して判定し、画面では残作業を簡潔に伝える。

## 地域の協力を進める流れ

1. 店舗が「藍染の写真と英語紹介を改善したい」とヘルプを出す。
2. 協力者ができること、納期、報酬案を提案し、店舗が採用する。
3. 対象商品、作業、対価、期限、素材の利用範囲、承認方法に合意する。
4. 協力者が担当範囲の原稿・写真を用意し、店舗が確認して公開する。
5. 予約に必要な通訳などの担当を調整し、開催する。
6. 合意した報酬と支払状況を双方が確認し、実績や次の協力につなげる。

不採用・修正、協力者の辞退・交代、体験の取消、報酬の対象期間終了でも、担当と金額の根拠を追えるようにする。個別の制作・通訳などの報酬は、実際の合意と支払いに基づいて確認する。

## 実装の順序と受入条件

| 順序 | 項目 | 最初に満たす条件 |
| --- | --- | --- |
| 先行 | 既存予約と提供者運営 | API接続、配備・有効化、予約・決済・取消・精算を旅行者・店舗・事務局で通して確認できる |
| 先行 | 代理での掲載準備 | 本人未登録の準備案件を作り、限定プレビュー、修正、代表者の受入、販売準備へ進める。既存店舗を重複作成しない |
| 初期 | 協力を運用で試す | 招待した協力者との仕事内容・対価・期間・素材利用・支払状況を非公開で記録できる |
| 次 | 協力者の参加と提案 | 既存アカウントで参加し、技能・言語・実績を示せる。募集、提案、採用、辞退、完了と通知を扱える |
| 次 | 共同制作と権限 | 商品・作業に必要な範囲だけを共有し、店舗の承認と変更履歴を残せる。終了・交代後は権限を取り消せる |
| 次 | 合意と報酬の確認 | 対象、計算根拠、期間、取消時の扱い、支払方法を合意し、当事者が確認できる。過去に適用した条件を後の変更で書き換えない |
| 次 | 開催時の協力 | 予約ごとの通訳等の依頼・候補・確保・交代を扱い、担当者へ必要な開催情報だけを共有できる |
| 次 | 紹介と参加の見える化 | 紹介リンク・QR・共有案内、本人が同意したクレジットや活動報告を用意できる |
| 後続 | 外部販売との接続 | OTA掲載資料と販路別の商品参照を整理し、既存サービスを比較したうえで在庫・予約連携を判断できる |

通訳等の確保が必須の体験は、予約承認までに何を確認するかを別途合意する。紹介報酬を採用する場合も、予約に紐づく合意・成果の記録と訂正方法を決める。UTMだけで報酬を確定しない。

## 初期運用と拡張の判断

既存の予約基盤と掲載準備を整えながら、少数のヘルプをフォーム・個別連絡・非公開記録で試す。その結果から「参加 → 募集 → 提案 → 合意 → 制作・承認 → 報酬確認」をサイトへ移す。公開の募集市場、自動報酬分配、OTA在庫の自動連携は、実際の件数・例外・作業量を確認して範囲を決める。

支援を減らすときは、本人の希望と運営能力に応じて仕事ごとの担当を変える。予約件数だけで自立や料金変更を自動判定しない。店舗が販売者であることを保ち、商品や予約履歴を作り直さずに運営分担を変えられるようにする。

NIHOの運営分、制作・紹介・通訳の対価、決済・販路費用は区別する。初期制作と予約ごとの継続支援の作業量を測り、支援範囲と対価を見直す。具体的な事業数値・試算・未確定の料金案は非公開の記録で管理する。

## 担当するシステムとデータの扱い

[構成とデータ境界](../../docs/architecture.md)に従い、niho-experienceは参加者向けの画面・公開表示・選別されたAPI接続を担当する。認証、所有権・権限、原稿・商品・予約・決済の正本はNIHO共通基盤を使う。協力合意・報酬情報を追加するときも、データの所属・保持・公開範囲を合意してから必要なAPIを設計する。

本人未登録の掲載準備案件については、運営用データとしての保管、既存店舗との照合、代表者への接続、辞退・中止時の素材削除と保持範囲を先に決める。公開サイトに別の認証元・決済台帳・権限の正本を作らない。

公開リポジトリには一般化した役割・画面・受入条件を置く。事業の収支試算、未確定の料率、実予約数、提携先の条件・連絡先、未公開原稿・個別の合意、内部スキーマはGit管理外の非公開台帳に保管し、PR本文やfixtureにも載せない。

## 次の作業

1. 関連Issueの残作業を「画面」「API接続」「配備・受入」に分けて確認する。
2. 店舗の確認ページと、事務局の掲載準備一覧の画面案を作る。
3. 撮影依頼など一件の例で、依頼・提案・合意・制作・支払確認までの運用を試す。
4. 初期募集の公開範囲、権限・承認、対価と支払方法、準備案件の保持・引継ぎを合意する。
5. 合意後、NIHO共通基盤の契約とexperienceの画面へ分けて実装Issue化する。

完了の判断には、店舗へ入力を求めた回数、掲載準備から販売開始までの時間、途中で止まった理由、予約一件の支援時間、協力者との継続意向を見る。運用の観察結果を次の実装範囲に反映する。
